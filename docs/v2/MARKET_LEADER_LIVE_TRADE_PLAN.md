# 주도주 AI 실전 매매 연동 계획 (Market Leader AI Live Trade Plan)

## 1. 개요 및 목적
본 문서는 모의 시뮬레이션에서 검증된 '주도주 AI' 전략을 실제 키움증권 계좌와 연동하여 실전 자동 매매 시스템으로 확장하기 위한 핵심 고려 사항 및 단계별 개발 로드맵을 정의합니다.

기존 '보유종목' 메뉴와는 독립적으로 작동하는 '실전 매매 전용 파이프라인'을 구축하여, 다중 진입(Multiple Lots) 및 전략별 개별 청산을 완벽히 통제하는 것을 목표로 합니다.

---

## 2. 핵심 고려 및 설계 사항

### 2.1 물리적 계좌 vs 논리적 장부 분리 (최대 난제 해결 방안)
**문제 정의 (가장 중요한 도전 과제):**
실제 키움증권 계좌에서는 동일 종목을 다른 날짜에 추가 매수하면 '하나의 종목(평단가 및 총 수량 합산)'으로 병합되어 표시됩니다. 하지만 본 시스템은 각 진입(추천일)마다 독립적인 D-Day와 목표 수익률을 추적하므로, 시스템 상에서는 이를 엄격히 분리해서 관리해야 합니다.

**구체적 구현 방안 (Ticket-Based Ledger System):**
1. **고유 티켓(Ticket) 발급:** 종목 매수 시그널이 발생하여 매수 주문을 전송하면 시스템 DB(`live_trade_tickets`)에 고유한 `ticket_id`를 발급하고 초기 주문 정보를 기록합니다.
2. **당일 체결 정산 (Daily Execution Reconciliation):** 장 마감 직후(15:35), 키움 API를 호출하여 당일 매수 주문의 **실제 체결 수량**과 **정확한 체결 평균가**를 가져옵니다. 주문 수량과 실제 체결 수량을 대조하여 DB 티켓을 최종 업데이트(부분 체결 반영)하며, 미체결 시 상태를 `FAILED`로 처리하여 장부 오차를 원천 차단합니다.
3. **독립적 청산 조건 스캔:** 스케줄러는 매일 전체 잔고가 아닌 **개별 티켓 단위**로 스캔합니다. 즉, 계좌의 평균 단가가 아닌 `해당 티켓의 매수 체결가`를 기준으로 목표 수익률(Take-Profit) 도달 여부를 계산하고, `해당 티켓의 진입일`을 기준으로 D-Day 종료 여부를 판별합니다.
4. **부분 매도(Partial Sell) 실행:** 특정 티켓이 청산 조건(D-Day 또는 익절)을 만족하면, 시스템은 계좌에 있는 해당 종목의 전체 수량이 아닌 **DB에 기록된 해당 티켓의 `매수 체결 수량`만큼만 정확히 떼어내어 키움증권에 매도 주문**을 전송합니다.
5. **티켓 소멸 및 잔고 동기화:** 매도 체결이 완료되면 해당 티켓의 상태를 `CLOSED`로 변경합니다. 시스템의 '활성 티켓 총 수량 합산'이 키움증권의 '실제 보유 잔고 수량'과 일치하는지 대조하는 무결성 검증(Daily Sync Check)을 매일 수행합니다.

### 2.2 리스크 관리 및 엣지 케이스 (Risk Management & Edge Cases)
* **청산 원칙 (Take-Profit & Time-Stop):** 별도의 가격 기반 손절선(Stop-Loss)은 설정하지 않으며, 오직 '설정된 목표 수익률 도달(익절)' 또는 '최대 보유일 도달(기간 청산)' 두 가지 조건에 의해서만 청산을 실행합니다.
* **미체결 및 슬리피지:** 매도/매수 주문 시 유동성 부족으로 인한 미체결(Partial Fill) 처리 로직 및 재시도 메커니즘 구축.
* **수동 개입 대응:** 사용자가 HTS/MTS를 통해 수동으로 매도하거나 비중을 조절했을 경우, 시스템 장부 수량과 실제 잔고 불일치 시의 예외 처리(Alert 및 수동 동기화 기능).

### 2.3 매매 스케줄링 (모의매매 파이프라인 통합)
* **진입 (Entry - 모의매매 크론 연동):** 실전 매매를 위한 별도의 종목 발굴 스케줄러(Cron)를 중복 실행하지 않습니다. 기존 모의매매 파이프라인이 전 카테고리를 대상으로 종목을 선별할 때, **실전 매매용으로 선택된(활성화된) 단일 전략에 해당하는 종목이 선별되면 그 즉시 실전 매수 주문 파이프라인으로 넘겨 실행**합니다.
* **청산 (Exit):** 매일 정해진 시간(예: 09:05 시초가 소화 직후 또는 15:15 종가 직전)에 장부를 검사하고 조건 충족 Lot 일괄 매도 처리.

## 3. 단계별 개발 로드맵 (Phases)

### Phase 1: 아키텍처 및 내부 장부(Ledger) 설계 (DB & 백엔드)
가장 기본이 되는 데이터 모델을 설계하고 물리적 잔고의 의존성을 분리합니다.
1. **DB 스키마 구성**
   * `live_trade_tickets` 테이블 생성: `ticket_id`, `stock_code`, `entry_date`, `entry_price`, `quantity`, `strategy_category`, `target_exit_date`, `status`(ACTIVE, CLOSED) 관리.
   * `live_trade_strategies` 테이블 생성: 활성화할 단일(Single) 전략을 1개만 지정하며, 해당 전략의 1회 매수 금액, 최대 보유일, 목표 수익률(Take-Profit) 설정 값 보관 (손절선 배제).
2. **Core Service 구조 잡기**
   * 논리적 장부의 C/R/U/D 및 키움 실제 잔고와 비교하는 `LiveTradeLedgerService` 초안 작성.

### Phase 2: 실전 매매 전용 대시보드 구축 (UI/UX)
기존 포트폴리오(보유종목) 메뉴와 분리된 전용 관제 센터를 제작합니다.
1. **독립된 실전 매매 리스트 (Visual Separation):** 사용자가 모의매매 내역과 혼동하지 않도록 UI 상에서 '실전매매' 탭을 완벽히 분리합니다. 모의 데이터가 섞이지 않고 **오직 실제 키움증권 계좌로 매매된 실전 데이터(DB)만을 독립적으로 렌더링**하도록 데이터 소스를 철저히 격리합니다.
2. **제어판 (Control Center):** 드롭다운(Select) 방식의 '단일 전략 선택' UI 구현. 선택된 전략의 모의매매 데이터 기반 'AI 최적 파라미터 추천(예상 승률, 예상 평균수익, 최적 목표가 및 보유일)' 정보 연동.
3. **논리적 운용 현황 보드 (Ticket View):** 종목 기준이 아닌 **진입 단위(Ticket) 리스트 뷰** 구현. 티켓별 매매 생애 주기에 따른 4단계 진행 상태(`⏳매수중`, `🟢보유`, `⚡매도중`, `✅청산`) 명시적 표기.
4. **성과 추적 보드:** 실제 계좌의 체결 내역 기반 실현 손익 및 승률 통계 화면.

### Phase 3: 매매 실행 엔진 구현 (Execution Engine)
설정된 규칙과 내부 장부를 기반으로 키움 API에 실제 주문을 전송합니다. 개발 시 **키움 REST API 표준 규격**을 엄격히 준수합니다.

1. **자동 매수 파이프라인 (조건부 지정가 + 1틱):** 
   * **모의매매 크론 연동:** 기존 모의매매 스케줄러에서 AI 선별 성공 시 실행. (만약 모의매매 선별 로직이 실패/누락된 경우, 당일 실전 매매 진입을 안전하게 스킵하고 텔레그램 경고 발송).
   * **API 호출 규격 (`kt10000` 신규매수):** 선별된 종목 중 '활성 전략'과 일치하는 종목에 대해 투자 수량을 계산하고 매수 주문을 전송합니다.
     - `trde_tp`: **'05' (조건부 지정가)**
     - `ord_uv`: **'현재가 + 1틱'** (`getTickSize(price)` 적용)
     - `cond_uv` 파라미터는 전송 시 반드시 배제(오류 방지).
   * **주문 및 체결 검증 (Reconciliation):** 조건부 지정가는 장 종료 시 동시호가로 최종 체결되므로 미체결에 대한 장중 정정/취소 주문 로직은 불필요합니다. 단, **매일 15:35에 키움 API(예: `opt10075` 또는 `opt10077`) 체결 내역을 조회하여 당일 주문의 '실제 체결 수량'과 '체결 평단가'를 가져와 장부(Ticket)를 최종 확정(Update)합니다.** 실제 체결 수량이 0인 경우 티켓 상태를 `FAILED`로 변경합니다.

2. **자동 매도 파이프라인 (이원화된 청산 로직):**
   * **[Type A] 목표 수익률 도달 시 (Take-Profit 익절):**
     - 웹소켓 시세 감시 중 피크 수익률이 목표치에 도달할 경우 즉시 발동.
     - **API 호출 규격 (`kt10001` 신규매도):** `trde_tp`: **'00' (지정가)**, `ord_uv`: **'현재가'**
       - ⚠️주의: 매도 주문 시 `cond_uv`(스톱가격) 파라미터를 절대 포함하면 안 됨 (407022 에러 발생).
     - **미체결 정정 루프 (`kt10002` 매도정정):** 매수 호가 잔량 부족 등으로 지정가 미체결이 발생할 경우, **1분 주기로 미체결 내역의 원주문번호(`orig_ord_no`)를 스캔하여 갱신된 새로운 '현재가'(`mdfy_uv`)로 매도 정정 주문**을 체결될 때까지 반복 실행.
   * **[Type B] 최대 보유일 도달 시 (Time-Stop 기간 청산):**
     - 목표가에 도달하지 못하고 청산일(D-Day)에 도달했거나, 시스템 오류 등으로 인해 청산일을 초과하여 보유 중인 모든 티켓을 스캔.
     - **매일 오후 3시(15:00) 정각 발동 (`kt10001` 신규매도):** `trde_tp`: **'05' (조건부 지정가)**, `ord_uv`: **'현재가'**. (장중 미체결되더라도 3시 20분 동시호가에 시장가 체결되므로 정정 불필요).
   * **수량 불일치 대응 (Quantity Mismatch Contingency):** 실제 잔고 수량이 티켓의 매도 대상 수량보다 부족할 경우(예: 사용자의 임의 수동 매도), **현재 남은 실제 보유 잔고 전체를 매도(최대 가용수량 매도)** 처리하고 텔레그램으로 경고(Warning) 발송. 최종 매도 완료 시 Ticket 상태 `CLOSED` 변경.

### Phase 4: 시세 최적화 및 시스템 정합성 확보 (Safety & Sync)
안정적인 무인 매매를 위한 실시간 시세 처리 및 페일세이프(Fail-Safe) 기능.
1. **시세 처리 최적화 (Websocket vs Polling):** 
   * 목표 수익률(익절)에 도달하자마자 정확한 타이밍에 매도할 수 있도록, **보유 중인 종목(HOLDING)**에 한해서만 키움증권 **웹소켓(WebSocket) 실시간 시세**를 구독하여 틱 단위로 가격을 감시.
   * 반면, 당일 OHLCV 갱신이나 일일 최고가/현재가 차트 업데이트용 데이터는 웹소켓이 아닌 **정기적인 폴링(Polling) 주기**를 통해 비동기 업데이트하여 불필요한 시스템 리소스 및 API 낭비를 방지.
2. **Daily Sync Check:** 매일 장 시작 전, 키움 실제 잔고의 총 수량과 `live_trade_tickets`의 보유 수량 총합을 대조.
3. **텔레그램 알림 강화:** AI 선별 에러, 신규 주문 전송, 수량 불일치, 체결 확인 등 전 과정 즉각 리포팅.
4. **Kill-Switch (긴급 중단):** 치명적 오류 발생 시 자동 매매를 원천 차단하고 기존 포지션만 유지 또는 시장가 전량 청산하는 비상 정지 기능.
